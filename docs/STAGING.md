# Тестовый контур (staging)

Руководство по устройству, настройке и работе с тестовой копией игры «Депная». Документ написан для владельца проекта простыми словами.

---

## Зачем нужен тестовый контур

Когда в игру добавляются крупные новинки (новые азартные игры, переработка механик, изменения баланса), их нельзя выкатывать сразу живым игрокам: любая ошибка может испортить баланс или уронить сервис.

Для этого создаётся **тестовый контур (staging)** — точная изолированная копия игры для разработчика и владельца:
- разработчик спокойно проверяет код и дорабатывает сложные функции;
- владелец заходит в тестового бота со смартфона, щупает новинку руками и утверждает её;
- боевая версия для обычных игроков продолжает работать стабильно и без сбоев.

---

## Как устроен тестовый контур

| Компонент | Боевая версия (production) | Тестовая версия (staging) |
|---|---|---|
| **Ветка в Git** | `main` | `staging` |
| **Telegram-бот** | Боевой бот (для всех игроков) | Отдельный тестовый бот (только для тестов) |
| **Клиент (интерфейс)** | GitHub Pages (обновляется только из `main`) | Раздаётся напрямую тестовым сервером Railway |
| **Сервер** | Railway (окружение `production`) | Railway (отдельное окружение `staging`) |
| **База данных** | SQLite на боевом томе Railway | Отдельная SQLite на **собственном** томе staging |
| **Платежи Stars** | Включены | **Отключены** (включаются только по флагу) |
| **Отличия на экране** | Обычный интерфейс | Яркая красная лента **«ТЕСТОВЫЙ СЕРВЕР»** в углу |

### Особенности работы тестового режима (`APP_ENV=staging`):
1. **Клиент не зависит от GitHub Pages:** при значении `APP_ENV=staging` сервер сам отдаёт файлы игры (HTML, скрипты, стили) прямо со своего адреса на Railway. Боевой клиент на GitHub Pages вообще не затрагивается.
2. **Адрес API подменяется автоматически:** сервер на лету настраивает интерфейс так, чтобы все запросы шли на тестовый адрес.
3. **Безопасность файлов:** сервер отдаёт только файлы из строгого белого списка (страницы игры, скрипты, стили, шрифты, картинки). Исходный код сервера и служебные файлы наружу не отдаются.
4. **Защита от случайных трат:** реальные платежи Telegram Stars отключены. Даже если нажать кнопку покупки, списания реальных звёзд не произойдёт (для проверки платежей при необходимости выставляется `STAGING_ALLOW_PAYMENTS=1`).
5. **Проверка состояния:** адрес `/health` возвращает статус `{"ok": true, "env": "staging"}`.
6. **Удобство тестирования:** владелец со своего Telegram-аккаунта (`OWNER_CHAT_ID`) может в любой момент выдать себе любое количество фишек или кристаллов скрытыми командами (`/give 100000`, `/givegems 5000`, `/player` и др.).

## Схема потока работы (Workflow)

```
[Ветка feature/*] (разработка новинки)
        │
        ▼ (обычный merge, без force push)
[Ветка staging] ──> Автодеплой на Railway (окружение staging)
        │
        ▼ (проверка владельцем в тестовом боте)
   [Одобрено?]
   ├── ДА ──> Вливаем [feature/*] напрямую в [main] ──> Боевой деплой
   └── НЕТ ─> Дорабатываем в [feature/*] и снова вливаем в [staging]
```

### 5 шагов рабочего процесса:
1. **Новая функция делается в отдельной ветке `feature/*`** (например, `feature/new-game`).
2. **Ветка вливается в ветку `staging`** обычным слиянием (merge) без перезаписи истории (`force push` строго запрещён). Railway автоматически собирает и запускает обновление на тестовом сервере.
3. **Владелец проверяет новинку** в тестовом боте со своего аккаунта.
4. **Когда новинка одобрена**, именно ветка `feature/*` вливается в `main`. Ветка `staging` целиком в `main` не вливается, так как в `staging` могут параллельно проверяться другие незаконченные функции.
5. **Время от времени `main` вливается в `staging`**, чтобы тестовая ветка не отставала от боевой.

> Перед слиянием в `main` обязательно запускаются все автоматические тесты и проверки. В CI (GitHub Actions) тесты бегут как на ветке `main`, так и на ветке `staging`.

## Пошаговая инструкция для владельца (настройка один раз)

Вам понадобится выполнить эту процедуру один раз.

### Шаг 1. Создать тестового бота в Telegram
1. Откройте в Telegram официального бота **@BotFather** и отправьте команду `/newbot`.
2. Задайте имя (например, `Депная Тест`) и юзернейм (например, `..._staging_bot` или `..._test_bot`).
3. Скопируйте полученный токен бота.
   > **Важно:** никогда не присылайте этот токен в чаты и не сохраняйте в файлы репозитория! Он вводится только в панель Railway.
4. Настройку кнопки меню и Mini App в @BotFather мы сделаем чуть позже (в Шаге 6), когда Railway выдаст адрес тестового сервера.

---

### Шаг 2. Ветка staging в Git
Ветку `staging` на GitHub создаёт ведущий разработчик (из текущей `main`), вам делать ничего не нужно. Если её по какой-то причине нет, команда такая: `git push origin main:staging`.

---

### Шаг 3. Создать окружение staging в Railway
1. Откройте проект вашей игры в [Railway](https://railway.com/).
2. В верхней части экрана нажмите на переключатель окружений (**Environments**) и выберите **New Environment**.
3. Назовите его `staging`.
4. Внутри окружения `staging` появится сервис приложения.
5. **Обязательно создайте НОВЫЙ том (Volume) для базы данных:**
   - Нажмите правой кнопкой на холсте или используйте меню добавления → выберите **Volume**.
   - Подключите этот том к сервису staging.
   - Укажите путь монтирования (Mount Path): `/data`.
   > **Критически важно:** ни в коем случае не подключайте к тестовому окружению том из боевого окружения! У тестового сервера должна быть своя независимая база данных.

---

### Шаг 4. Настроить сборку сервиса в Railway
В настройках сервиса окружения `staging` (вкладка **Settings**):
1. **Source Repo / Branch:** выберите ветку `staging`.
2. **Root Directory:** оставьте пустым (корень репозитория).
3. **Dockerfile Path:** добавьте в переменные сервиса или укажите в настройках сборки файл `Dockerfile.staging` (переменная `RAILWAY_DOCKERFILE_PATH=Dockerfile.staging`).
4. **Public Domain:** в разделе **Networking** нажмите кнопку **Generate Domain** (или подключите тестовый домен). Вы получите адрес вида `https://<адрес-вашего-сервиса>.up.railway.app`.

---

### Шаг 5. Задать переменные окружения staging
Во вкладке **Variables** сервиса `staging` добавьте переменные. 

> **Внимание:** значения ниже описаны как ориентир. Секретные ключи генерируйте заново, не копируйте боевые значения!

| Имя переменной | Что туда вставлять |
|---|---|
| `APP_ENV` | Слово `staging` (включает тестовый режим и раздачу интерфейса) |
| `BOT_TOKEN` | Токен **тестового** бота, полученный от @BotFather в шаге 1 |
| `WEBHOOK_SECRET` | Новый случайный ключ (сгенерируйте командой `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`) |
| `PUBLIC_URL` | Адрес вашего тестового сервиса из шага 4 (например: `https://<адрес-вашего-сервиса>.up.railway.app`, без косой черты в конце) |
| `WEBAPP_URL` | Тот же самый адрес тестового сервиса (так как клиент раздаётся самим сервером) |
| `ALLOWED_ORIGINS` | Тот же адрес тестового сервиса (например: `https://<адрес-вашего-сервиса>.up.railway.app`) |
| `DB_PATH` | `/data/players.db` (путь к базе данных на новом томе) |
| `TOMBSTONE_SECRET` | Новый случайный ключ (сгенерируйте командой `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`) |
| `MEMBER_REF_SECRET` | Новый случайный ключ (сгенерируйте командой `python3 -c "import secrets; print(secrets.token_hex(32))"`) |
| `OWNER_CHAT_ID` | Ваш числовой Telegram ID (чтобы вам были доступны скрытые команды начисления) |
| `RAILWAY_RUN_UID` | `0` (образ запускается не от root, а Railway создаёт том с правами root; с этой переменной база сможет записаться в `/data`, это приём из документации Railway, **не проверено** на этом проекте) |

Если после запуска в логе сервиса есть ошибка записи в `/data`, проверьте, что `RAILWAY_RUN_UID=0` задана и том подключён к сервису `staging`.

**Чего делать НЕЛЬЗЯ:**
- НЕ вставляйте боевой `BOT_TOKEN`;
- НЕ задавайте переменных бэкапов боевой базы (`BACKUP_PUBLIC_KEY` и т.д.);
- НЕ подключайте боевой том с реальными балансами игроков.

---

### Шаг 6. Настроить Mini App в @BotFather
Когда сервис staging задеплоился и получен публичный адрес:
1. Откройте **@BotFather** → `/mybots` → выберите вашего тестового бота.
2. Перейдите в **Bot Settings** → **Menu Button** → **Configure menu button**.
3. Укажите адрес тестового сервиса: `https://<адрес-вашего-сервиса>.up.railway.app`.
4. (Опционально) Через команду `/newapp` настройте прямое веб-приложение, указав тот же адрес.

---

### Шаг 7. Проверка работы
1. **Проверка API:** откройте в браузере страницу `https://<адрес-вашего-сервиса>.up.railway.app/health`.
   - Ответ должен быть: `{"ok": true, "env": "staging"}`.
2. **Проверка бота и приложения:**
   - Откройте тестового бота в Telegram и напишите `/start`.
   - Нажмите кнопку «Играть» (откроется Mini App).
   - В углу экрана должна отображаться яркая красная лента **«ТЕСТОВЫЙ СЕРВЕР»**.
   - Проверьте скрытую команду владельца в личке бота: `/give 50000` (баланс должен пополниться).
   - Сыграйте тестовые раунды — баланс боевой игры останется нетронутым.

## Правила безопасности

1. **Полная изоляция данных:** боевые токены, боевая база и боевой том никогда не подключаются к тестовому контуру.
2. **Никаких посторонних игроков:** тестовый бот предназначен исключительно для команды проекта. Не отправляйте ссылку на тестового бота обычным игрокам.
3. **Только тестовые данные:** в тестовой базе лежат искусственные балансы, которые можно сбрасывать в любой момент.
4. **Файлы в корне репозитория:** файлы `Dockerfile.staging` и `.dockerignore` расположены в корне репозитория. Боевой сервис Railway использует настройку `Root Directory = bot`, поэтому он эти файлы не видит и на боевой деплой они никак не влияют.
