# Архитектура: что где лежит

Карта для быстрого входа. Подробности и причины решений: `CLAUDE.md` (правила), `docs/JOURNAL.md` (история), `docs/API.md` (контракт), `bot/DEPLOY.md` (деплой).

## 1. Схема
Клиент (`index.html`, `css/*.css`, `js/*.js`, без сборщика) лежит на GitHub Pages и работает внутри Telegram WebApp. Сервер (FastAPI + бот, один процесс,
одна реплика) работает на Railway, данные в SQLite на томе. Единственный источник баланса и результата игры: сервер; личность только из подписанного `initData`.

## 3. Деньги
- Баланс меняется **только через `wallet`** внутри уже открытой транзакции `BEGIN IMMEDIATE`. Исключение: разовая миграция `_migrate_minute_accrual` в `core/migrations.py` (прямой `UPDATE`).
- Доход фермы начисляется поминутно и лениво: `db._accrue_conn` (через `wallet.credit`) вызывается в начале каждого запроса, затрагивающего игрока; фоновых заданий нет.
  Остаток `players.accrual_acc` в [-59, 0], за любые 60 минут ровно R. `GET /api/me` без полной минуты ничего не пишет в базу.
- Потолок баланса `MAX_SAFE_INT` (9007199254740991): клиент хранит числа точно, зачисление выше потолка обрезается.
- Общие функции лежат в `core/kernel.py` (`_accrue_write`, `_credit_capped`, `_add_xp`, `_register_player`); слои зависят только вниз: `games` и `features` импортируют `core`, друг друга и `db.py` не импортируют.

## 4. Шаблон партии (мины, блэкджек, краш, хило)
**Рекорды выигрыша:** единая точка записи личного рекорда (чистый выигрыш = выплата минус ВСЯ ставка раунда) это `core.kernel._record_best_win(conn, id, игра, ставка, выплата, now)`: один UPSERT, только если выигрыш строго больше сохранённого; вызывают `pay_and_xp(..., игра, ставка, now)` (краш, блэкджек: все поставленные суммы `wager`, хило), `mines_db._finish_game`, `play_keno`, `spin_roulette`; новая игра обязана вызвать её в своём месте выплаты (тест `test_best_wins.py` проверяет, что таблицу пишет только `kernel.py`). Рейтинг: `chat_db.chat_best_wins` и `GET /api/chat/best-wins` (участники те же, что у `chat_top`; отдельный маршрут, чтобы сбой рекордов не ломал рейтинг). Клиент: блок `#best-card` под рейтингом (`showBestWins`, тексты только `textContent`, игры по белому списку `BEST_GAMES`). В эталон golden SQL записи рекорда не входит (фильтр в `test_game_golden.py`).

Общий скелет лежит в `games/round_common.py` (без денег и правил игр): `Game` (имя игры, ошибка конфликта request_id, тексты запросов к `<игра>_games`
и `<игра>_actions`), `run_action` (закрытие просроченной, повтор по `(игрок, request_id)`: тот же id с другими параметрами даёт `RequestConflict`, `_register_player`,
`_accrue_write`, тело, запись ответа в `*_actions`), `settle_expired` (закрытие брошенной отдельной транзакцией, `precheck` для игр, которые сначала читают),
`close_expired` (фоновый проход), `read_state` (чтение с начислением), `active_row`, `latest_row`, `player_view`, `add_staked`, `pay_and_xp`, `run_tx`.
1. Таблицы `<игра>_games` и `<игра>_actions`; уникальный частичный индекс «одна активная партия на игрока».
2. Игра в `games/<игра>_db.py` задаёт ТОЛЬКО своё: тела действий (списание через `wallet.debit`, `ActiveGameExists`), формы ответов (`_view`, `_none_view`), `_finish` (окончание партии
   один раз по условию `status = 'active'`, затем `pay_and_xp`), правило «брошена ли партия», момент учёта `total_staked` (`add_staked`: сразу у блэкджека и краша, при первом ходе у мин и хило).
   Остаются в играх намеренно: мины (выплата зачисляется ДО отметки закрытия, порядок SQL другой, поэтому свой `_finish_game`), краш (чтение без транзакции во время полёта), все формулы выплат и XP.
3. Брошенная партия закрывается сама (`settle_expired_*` при запросе, `close_expired_*` раз в проход фоновой задачи); `/api/me` отдаёт `active_game` для возобновления.
4. `total_staked` и опыт по правилам игры (см. `CLAUDE.md`); скрытое состояние (мины, колода, точка краха) не попадает в ответы, логи и `/mydata`.
5. **Новая игра по шагам:** правила в `<игра>.py` + тесты математики; формула опыта в `xp.py`; таблицы в `core/schema.py`; `games/<игра>_db.py`: `GAME = Game("<имя>", <игра>.RequestConflict)`
   (имя добавить в `GAMES` в `round_common.py`), `_<игра>_active` (через `active_row`), `_view`/`_none_view`, `_finish` (UPDATE ... AND status = 'active', потом `pay_and_xp`), `_settle_in`,
   `settle_expired_<игра>` (`settle_expired`), `close_expired_<игра>` (`close_expired`), `_run_<игра>_action` (`run_action`), функции start/ход/cashout/state (`read_state`) + строка в фасаде `db.py`;
   очистка, экспорт и удаление в `purge_old_data`, `get_player_export`, `delete_player_data`; `active_game_of`; маршруты в `api.py`; пример в `docs/examples/<игра>.json` и раздел в `docs/API.md`;
   запись в `GAMES` и экран в клиенте; `privacy.html`. **Сначала добавь сценарии новой игры в `bot/test_game_golden.py`** (эталон `bot/testdata/game_golden.json`: ответы, таблицы, число и порядок SQL).

## 6. Клиент (`js/*.js`, классические скрипты)
Без сборщика и модулей: `index.html` подключает `js/00-config.js` ... `js/17-start.js` по порядку номеров, область видимости общая (карта файлов в шапке `js/00-config.js`). Метки версий `?v=` в `index.html` обновляет `python scripts/stamp_client.py` после любой правки клиента (иначе браузер соберёт страницу из старых и новых частей). **Серия входов** (`js/14-streak.js`): карточка «Награда дня» на титульном экране, данные только из `GET /api/streak`, сбор `POST /api/streak/claim` (пустое тело), фишки из ответа через `wdApplyBalance`, кристаллы в `shop.gems`; сценарий `streak_card`.
- **Покупка набора** (`js/13-wardrobe.js`, блок `wd-set-box` в листе предпросмотра): у части набора за кристаллы, если у игрока нет ни одной части этого набора, показывается «Весь набор «Название»: N 💎 (вместо M 💎 за все части)», M считается по каталогу; наборы берутся из `sets` уже существующего ответа каталога (новых запросов при показе экранов нет); подтверждение вторым нажатием, один `POST /api/cosmetics/buy-set`; сценарий `set_buy`.
- **Пригласить друга** (`js/04-profile.js`, блок Referral; разметка в профиле): карточка с правилами из `rules` ответа `GET /api/referral` (числа не хардкодятся), кнопки «Отправить другу» (`tg.openTelegramLink` на `t.me/share/url`, запасной `openLink`) и «Скопировать ссылку» (при отказе буфера ссылка показывается текстом); загрузка ленивая, при показе экрана Профиль и не чаще раза в минуту (не при старте: сетевой журнал остальных сценариев не меняется); ссылка принимается только `https://t.me/…`; сценарий `referral_card`.
- **Подарки** (`js/13-gift.js`): в листе предпросмотра предмета за кристаллы кнопка «Подарить участнику беседы» (видна, только если приложение открыто из беседы), список участников с сервера (`GET /api/gifts/recipients`, метки `ref`), подтверждение вторым нажатием, один `POST /api/gifts/send`; сценарий `gift_send`.
- **Коллекции** (`js/13-wardrobe.js`): полоса коллекций над слотами («Листопад: 1 из 3» и как получить; данные `collections` из `/api/cosmetics/mine`), часть не получена: статус «Коллекция» вместо цены, подсказка в предпросмотре, покупки и подарка нет; эффект полного набора: все части собранной коллекции надеты, у корня атрибут `data-set-complete` (лёгкое мерцание названия на титульном экране, `prefers-reduced-motion` отключает). Награда дня сообщает о выданной части в карточке серии. Сценарий `collection_leaves` (сезон в e2e расширен в `e2e/server_boot.py`).
- **Имена верхнего уровня в `js/` общие для всех файлов и не должны повторяться** (повтор функции молча перекрывает прежнюю, повтор const ломает файл): проверяет `python scripts/check_js_globals.py` (CI). Секции в файлах секции помечены `// #region ... // #endregion` (свёртываются в редакторе): константы и форматирование, **ЯДРО**, ввод суммы и фишки,
панель ставок над клавиатурой, рулетка, баланс и профиль (`/api/me`), рейтинг, ферма, минутное начисление, мины, кено, блэкджек, краш, хило, гардероб, лобби и вкладки, встроенные игры, доступность, запуск.
- **ЯДРО** (начало файла): константы времени, Telegram (`tg`, `haptic`), форматирование (`spacedNumber`, `fitNumberFont`, `mmss`), сеть (`makeRequestId`, `postJson` с повтором при 429, `postMinesOnce`),
  общие каркасы игр: `fetchGameState` (GET состояния), `loadGameState` (загрузка при открытии, возврате и вручную, паузы 5 и 10 с), `postWithRetries` (до 3 попыток с одним `request_id`),
  `actionFailure` (текст при неудаче действия), `makeChipBar` (фишки ставки по серверному балансу) и **реестр игр** `registerGame`.
- **Реестр игр** `gameRegistry`: игра при объявлении своего состояния вызывает `registerGame({ id, state, render, busy, keepBalance })`. Ядро (`/api/me`, минутное начисление) обходит реестр:
  `anyRoundBusy` (идёт запрос или анимация: баланс на экране менять нельзя), `balanceSignature`, `syncGameBalances`. По именам игр ядро не знает (кроме `GAMES` с названиями и иконками для меню).
- Общее состояние `srv` (баланс, ставка дохода, уровень, `activeGame`), `tg`, `activeTab`, `currentGame`.
- Шаблон игры с партией (мины, блэкджек, краш, хило): `fetchXState` (`fetchGameState`) → `applyXState` → `loadX` (`loadGameState` с настройкой игры) → `xAct` (защита от двойного нажатия `if (x.busy) return`,
  `makeRequestId`, `postWithRetries(() => postMinesOnce(...))`, свой разбор успеха и анимация, неудача через `actionFailure`). Рулетка и кено (один запрос на раунд) остаются со своим каркасом: у них нет состояния партии.
- Панель ставок `setupBetPanel` (фишки T/10, T/2, T, 5T; ÷2, ×2, Макс/Готово) и защита тапов (`closeOnBackdropTap`, действие кнопки по нажатию при клавиатуре).
- **Баланс на экране меняется только после анимации**; запросы `/api/me` откладываются, пока идёт ход или анимация (`anyRoundBusy`).
- **Как добавить игру на клиенте:** экран `<section class="screen mines" data-screen="...">` в `index.html`; в `js/` секция игры (файл по порядку): `xEls` (элементы), состояние `x` (`balance`, `view`, `busy`, `inFlight`, `lastRequestAt`, `timer`, `loaded`, `error`)
  и сразу `registerGame({ id, state: x, render: renderX, busy: () => x.busy [|| x.animating] })`; `validXState`/`validXAction` (по `docs/API.md`); `fetchXState` и `loadX` через `fetchGameState` и `loadGameState`;
  `xAct` по образцу блэкджека; фишки через `makeChipBar`; запись в `GAMES` (название, иконка) и строка `if (started && screen === 'x') loadX('open')` в `showTab` (выбор игры: `selectGame`); пример ответа в `docs/examples/`; сценарий в `e2e/scenarios/`, затем `--record-net` для сетевого эталона.
- **Темизация (скины, косметика):** внешний вид слотов `card_back`, `chip`, `table`, `mine_icons`, `keno_ball`, `crash` задают CSS-переменные в блоке «переменные скинов» (`css/01-skins.css`)
  (`--card-*`, `--chip-*`, `--table-*`, `--wheel-*`, `--mines-*`, `--keno-*`, `--cr-*`; значения по умолчанию = стартовый вид, правила читают только переменные). `applySkins(equipped)` (ядро) ставит на `<html>`
  атрибуты `data-skin-<слот>` (значение = код надетого предмета, у стартового тоже) и опциональные `data-patina-<слот>="0..4"` (по объекту `patina`) после каждого успешного `/api/me` (`cosmetics.equipped` и `cosmetics.patina`) и при любой смене надетого; слоты `avatar_frame` и `badge` в `applySkins` не обрабатываются: рамка (`--avatar-frame`, тень вокруг аватара того же размера) и значок (`.rating-badge`, глиф рядом с именем) ставятся на сами элементы аватара и имени (`decorateAvatar`, `badgeEl`), у себя из `cosmetics.equipped`, у других из `cosmetics` участника в `/api/chat/top`.

## 7. Данные и приватность
Таблицы: `players` (+`accrual_acc`), `referral_codes`, `referrals` (рефералка: код и ссылка в `features/referral_db.py`, привязка и бонус в `core/referral.py`, квалификация в `features/referral_db.py:check_qualification`), `cosmetic_items`, `achievement_progress` (счётчики и серии достижений «Клуб ×1.01»; удаляется с игроком), `cosmetic_equipped`, `cosmetic_prefs`, `cosmetic_actions` (косметика: предметы и надетое хранятся, пока есть профиль, журнал действий 30 дней; удаляются с игроком), `cosmetic_purchases` (журнал оплат Stars: `charge_id` уникален; остаётся после удаления данных игрока 365 дней для споров и возвратов), `roulette_rounds`, `farm_purchases`, `keno_rounds`, `slot_rounds` (раунд Western Slot целиком в `round_json`), `mines_*`, `blackjack_*`, `crash_*`, `hilo_*`, `transfers`, `player_best_win` (рекорд выигрыша игрока: одна строка, пишет только `core.kernel._record_best_win`; удаляется с игроком, в копиях как вся база), `chat_members`, `bot_chats` (только chat_id групп),

**Краш с автовыводом:** `crash_start` с `target_x100` больше не решает раунд сразу: раунд активен, как ручной (`mode = 'auto'`). `crash.settle(crash, start, now, target)` закрывает его по серверному времени: при `T <= C` на `m >= T` выплатой ровно по T (даже при поздней проверке), при `T > C` проигрышем на `m > C`; `crash_cashout` работает и в авто-раунде (сначала `_crash_settle_in`, затем множитель на момент запроса, не выше цели). Закрытие ленивое (`crash_state`, `/api/me`, старт, вывод), одна транзакция, условие `status = 'active'` даёт одну выплату при параллельных запросах. `xp_multiplier`: авто, выигрыш: множитель выплаты, проигрыш: цель. Схема БД не менялась. Клиент: кнопка «Забрать» и индикатор «авто ×T» в том же месте, множитель на экране не выше цели (`crTarget100`), итог из ответа сервера. Тесты: `test_crash.py`, `test_crash_rtp.py` (метод и допуск в docstring), сценарии `crash_auto_manual`, `crash_visibility`.

**Удаление данных и переводы:** `delete_player_data` удаляет записи `transfers`, где игрок отправитель, а где он получатель, не удаляет, а заменяет `recipient` на `transfers.ANONYMOUS_ID` (0): суточный лимит отправителя считается по его записям, и сообщник-получатель не должен мочь его обнулить. Обезличенные записи уходят по общему сроку хранения (30 дней). Индекс `idx_chat_members_telegram (telegram_id, last_seen)` обслуживает поиск имени второй стороны, выгрузку и удаление. `/api/me`: проверка просроченных игр у мин и блэкджека сначала читает (`precheck`), блокировка записи только если игра просрочена (как у хило и краша).
Меняется то, что хранится о людях или видят другие игроки: в той же задаче правь `privacy.html` (разделы 2, 4, 5) и дату.
