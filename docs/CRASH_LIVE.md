# CRASH_LIVE.md — живой краш (проект, решения владельца 2026-10-09)

Статус: **проект, не реализован.** Цель владельца: краш переделать в игру, которая «крутится постоянно» на сервере, ставки делаются вживую, игроки видят ставки и выводы друг друга в реальном времени.

## 1. Решения владельца (2026-10-09)
- **Комната у каждой беседы.** Игроки видят только ставки своей беседы (ключ комнаты = подписанный `chat_instance` из initData, как у рейтинга беседы и бонуса беседы).
- **Имена в ленте ставок как в рейтинге беседы** (имя из Telegram, то, что и так видят участники беседы). `privacy.html` обновить.
- **Доказуемая честность:** перед раундом сервер публикует хэш секрета, из которого получена точка краха; после краха раскрывает секрет. Любой может проверить, что точку не подменили.
- **Раунды идут всегда**, комната может быть пустой, фальшивых игроков и подставных ставок нет.

## 2. Толкование решений (ведущий, можно поменять)
- «Идут всегда» = цикл раундов комнаты работает, пока в комнате есть наблюдатель (открытое соединение) или недавняя ставка; через 60 с без наблюдателей цикл доигрывает раунд и засыпает, при следующем входе стартует сразу. Иначе тысячи пустых бесед держали бы сервер занятым зря. Игрок этого не видит: при входе комната уже «играет».
- Игра открыта в личном чате (нет `chat_instance`): **личная комната из одного игрока**, тот же движок, ленты чужих ставок нет.
- Комнат на сервер конечное число: потолок активных комнат и соединений (раздел 7), сверх потолка вход отвечает «комната занята, повторите».

## 3. Раунд (сохраняем все числа сегодняшнего краша)
- Множитель `m100(t) = floor(100 * 2 ** (t / 6000))`, не больше ×250 (как в bot/crash.py). Точка краха из `crash_from_u(u)`, RTP 36/37 не меняется. Запас сети `GRACE_MS = 150` и «одно эффективное время» во всех проверках.
- Фазы: **приём ставок** (8 с, предложение ведущего) → **полёт** (до точки краха) → **итог** (4 с, показ краха и раскрытие секрета) → следующий раунд. Длительности в `bot/economy_config.py`.
- Ставка: одна на игрока за раунд (в версии 1), только в фазу приёма; необязательная цель автовывода (как сейчас, `target_x100` не меньше 101). Ручной вывод в полёте. Ставка не меньше 1 и не больше CRASH_MAX_BET.
- Деньги: ставка списывается через `wallet.debit` при подаче, выплата через `wallet.credit` при выводе (ручном или на цели); при краше выплаты нет. Опыт и `total_staked`, рекорд выигрыша (`_record_best_win`), лимит частоты и идемпотентность по `request_id` как у остальных игр. Баланс меняет только wallet.
- Точка краха нигде не появляется до конца раунда: ни в ответах, ни в ленте, ни в логах, ни в /mydata.

## 4. Доказуемая честность
- На каждый раунд комнаты: случайный секрет `seed` (32 байта, `secrets`). `commit = sha256(seed)` публикуется до открытия приёма ставок. Точка краха: `u = int.from_bytes(hmac_sha256(seed, b"crash")[:7], "big") % M`, `crash_x100 = crash_from_u(u)`. После краха публикуется `seed`; клиент (и любой желающий) проверяет хэш и точку формулой, текст формулы показывается в игре.
- Честная оговорка для игроков: проверяется, что точка не менялась после публикации хэша; распределение (RTP 36/37) задано формулой и тестами сервера.

## 5. Данные (схема, миграция CREATE TABLE IF NOT EXISTS)
- `crash_rounds(id, room_key, seed_hash, seed, crash_x100, bet_open_ms, flight_start_ms, crash_ms, status)`; `crash_x100` и `seed` читает только серверный код, наружу после краха.
- `crash_bets(round_id, telegram_id, bet, target_x100, cashed_x100, payout, status, request_id, created_at_ms)`, ключ (round_id, telegram_id); имя игрока для ленты берётся при отдаче, не копируется.
- `room_key`: хэш `chat_instance` (HMAC), сам идентификатор беседы в этих таблицах не хранится; личная комната: хэш id игрока.
- Старые `crash_games` остаются в базе до очистки по сроку хранения (как сейчас), активные старые игры при выкладке закрываются (ставка возвращается), новых не создаётся.
- Хранение: раунды и ставки комнат 30 дней (как раунды игр), /mydata (ставки игрока), /deletemydata, очистка purge, test_legacy_migration NEW_TABLES, `privacy.html`.

## 6. Движок и трансляция
- Движок внутри процесса приложения (Railway, один экземпляр): менеджер комнат + задача asyncio на комнату; события «открыть приём», «начать полёт», «автовывод по цели», «краш» ставятся на точное время, а не опросом. Автовыводы и итог раунда выполняются транзакциями BEGIN IMMEDIATE.
- Восстановление после рестарта: незакрытые раунды читаются из базы; время краха известно (старт + расчёт), просроченные закрываются (невыведенные ставки проиграны, автоцели ниже краха выплачены), затем цикл продолжается.
- Транспорт: WebSocket (`/ws/crash`), подпись initData в первом сообщении (не в адресе), типы сообщений: снимок комнаты (фаза, времена, хэш, текущие ставки), «ставка», «вывод», «краш (точка, секрет)», пинг. Запасной путь: `GET /api/crash/live?since=<номер события>` быстрым опросом, если WebSocket недоступен. Клиент рисует кривую локально по серверному времени старта и поправке часов, сервер присылает только события.
- Лимиты: сообщений в секунду на соединение, размер сообщения, число соединений на игрока и на комнату, потолок активных комнат, кольцевой буфер событий комнаты.

## 7. Этапы (каждый выкладывается отдельно, с тестами и откатом)
1. **Движок и API без WebSocket:** таблицы, цикл комнаты с внедряемыми часами и генератором для тестов, ставка, вывод, автовывод, закрытие раунда, честность (хэш и раскрытие), `GET /api/crash/live` и `POST /api/crash/bet`, `/cashout`; старый краш отключается флагом. Тесты: деньги (сумма ставок и выплат), RTP на большом числе раундов, гонки ставок и выводов, восстановление после рестарта, идемпотентность, точка краха не утекает.
2. **Трансляция:** WebSocket с лимитами и запасной опрос; тесты соединений.
3. **Клиент:** новый экран краша (лента ставок комнаты, фазы, обратный отсчёт, хэш и проверка), скины краша без изменений; e2e (новые сценарии вместо crash, crash_auto_manual, crash_visibility, shared_core), эталон сети.
4. **Выкладка и уборка:** закрытие старых активных игр, удаление старых маршрутов (ответы 410), `privacy.html`, `terms.html`, API.md, ARCHITECTURE.md, журнал.
5. **Нагрузочный прогон:** сотни соединений и комнат на локальном сервере, замер задержки и расхода.
